New to Behat?

Behat checks your website the way people use it

Behat is a PHP tool for behaviour-driven development. You describe how your site should behave, in plain English, and Behat checks that it does.

Plain-text scenarios

Developers, testers and clients read the same file.

A browser to drive

Mink drives a fast HTTP client, or a real browser when the page needs JavaScript.

Runs on every change

In CI, a broken journey fails the build before it reaches your visitors.

New to Behat?

Gherkin: the language of a scenario

  • Feature names what the site does
  • Scenario is 1 example of it
  • Given sets up, When acts, Then checks
  • And continues the line before

Each line under a scenario is a step.

Feature: News articles
  Editors publish news for visitors.

  Scenario: Editor publishes an article
    Given I am logged in as a user with the role "editor"
    When I visit "/node/add/article"
    And I fill in "Title" with "Melbourne meetup"
    And I press "Save"
    Then I should see the success message "Saved"

New to Behat?

Behind every step is PHP code

Behat matches each step to a PHP method by its pattern, then runs the method.

Behat Steps is that code, already written and tested.

# The step in your feature file
When I visit "/"

// The step definition Behat runs for it
#[When('I visit :path')]
public function pathVisit(string $path): void {
  $this->getSession()->visit($this->locatePath($path));
}

// :path captures "/", and Mink opens the page

Architecture

Inside the package: 4 layers

Each layer depends only on the layers below it.

your project
FeatureContext, with your own steps.
Extends 1 of the 3 shipped contexts.
contexts
WebRawContext → WebContext → DrupalContext.
Each adds to the one before, and together they reach every layer below.
src/Steps
What a scenario can say.
57 step traits, and the 13 helper traits behind them.

Plugs the library into Behat and Mink.
Reads your behat.php and sets each scenario's backend order.
src/Backend
Reaches the site: drupal, drush, blackbox.
Uses no Behat or Mink code.
your site
The website under test.

Architecture

Why it's built in layers

Steps reach the site through a capability

So 1 step runs in-process, over Drush or on a backend of your own.

Backends know only the site

They use no Behat or Mink code, so they work outside a test run too.

Web steps sit apart from Drupal steps

A site that isn't Drupal extends WebContext and gets only the steps it can use.

A linter fails any code that depends on a layer above it.

Architecture

A capability is 1 job, written as an interface

Clearing caches, creating content, running cron. A backend provides a job by implementing its interface.

35 capabilities: 11 any backend may provide, 24 only a Drupal backend.

// The job
interface CacheCapabilityInterface {
  public function cacheClear(): void;
  public function cacheClearBin(string $bin): void;
  // and 3 more
}

// The step asks for the job
#[Given('the cache has been cleared')]
public function cacheClearAll(): void {
  $this->backendFor(CacheCapabilityInterface::class)
    ->cacheClear();
}

Architecture

Same step, any backend

@backend:drush moves Drush to the front for 1 scenario. The steps stay the same.

A backend starts only when a step first needs it, and your own backend serves the shipped steps.

// behat.php: the order to try
'backends' => ['drupal', 'drush', 'blackbox'],

# features/cron.feature
@backend:drush
Scenario: The home page loads after cron
  Given the cache has been cleared
  When cron runs
  And I visit "/"
  Then the response status code should be 200

Architecture

Why a step asks for a capability

Drupal Extension picked 1 driver for a whole scenario, with the @api tag. In 4.0, each step finds a backend for its own job.

  • A job the first backend can't do goes to the next one in your list
  • Your own backend serves every shipped step whose capabilities it implements
  • When no backend can do a job, the error names the capability and the order searched

Your scenarios describe the site. Your behat.php decides how to reach it.

Consistent language

Every step reads the same way

All 458 steps follow the same 19 wording rules.

  • A person's step starts with I: When I press the button "Save"
  • A step the site does starts with its subject: When cron runs
  • A value that picks 1 thing follows its noun: in the region "header"

A linter checks 13 of the rules in CI, so every new step follows them too.

Your own steps

1 context, a helper behind every step

Extend DrupalContext and every step is there. Your steps call the same 337 helpers.

Every public helper is listed in HELPERS.md, which ships with the package.

use Behat\Step\Given;
use DrevOps\BehatSteps\DrupalContext;

class FeatureContext extends DrupalContext {

  #[Given('a draft news article exists')]
  public function newsDraftExists(): void {
    $this->contentCreate('article', [
      'title' => 'Melbourne meetup',
      'status' => 0,
    ]);
  }

}

API testing

API steps get their own session

REST, JSON and XML steps run apart from the browser's cookies and page.

A header can take its value from the last response, so a token flow runs on the shipped steps.

    with the prefix "Bearer "
  And I send a REST "GET" request to "/api/resource"
  Then the JSON path "$.items" should exist
